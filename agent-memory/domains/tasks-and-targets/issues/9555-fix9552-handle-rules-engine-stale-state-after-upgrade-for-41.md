## Problem

Following a CHT upgrade, the rules-engine retained persisted state (rules state store and target state) generated by the prior version, so users could see incorrect or outdated target values (and potentially tasks) because calculations ran against stale cached state rather than current data.

## Root Cause

The rules-state-store persisted its state across version boundaries without recognizing that the stored target-state was produced under a previous version or for a stale target interval, so target computation reused incompatible cached state instead of recomputing it.

## Solution

Added handling in rules-state-store.js and target-state.js to detect stale rules-engine/target state after an upgrade and invalidate/rebuild it, ensuring target-state is regenerated from current data; covered with unit tests and an e2e target-accuracy scenario.

## Code Patterns

Stale-state detection and invalidation in shared-libs/rules-engine/src/rules-state-store.js and target-state.js — guard the persisted state with a version/interval check and rebuild the cached state when a mismatch is detected, rather than trusting persisted state blindly.

## Design Choices

Detect and selectively invalidate stale state on upgrade rather than forcing a full rules-engine rebuild unconditionally, avoiding the cost of recomputing all rules/targets when the existing state is still valid.
