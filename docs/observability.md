# Observability

CHT Agent uses [Langfuse](https://langfuse.com) for LLM tracing and pipeline monitoring, via the
Langfuse JS/TS SDK v5 (`@langfuse/tracing`, `@langfuse/otel`, `@langfuse/client`), which is
OpenTelemetry-based and targets the Langfuse v4 observations-first data model.

---

## Environment Variables

| Variable | Required | Description |
|---|---|---|
| `LANGFUSE_PUBLIC_KEY` | Yes (for tracing) | Langfuse project public key (`pk-lf-…`) |
| `LANGFUSE_SECRET_KEY` | Yes (for tracing) | Langfuse project secret key (`sk-lf-…`) |
| `LANGFUSE_BASE_URL` | No | API endpoint (default: `https://cloud.langfuse.com`) |
| `LANGFUSE_ENABLED` | No | Set to `false` to disable tracing entirely |
| `LANGFUSE_TRACING_ENVIRONMENT` | No | Tags every observation with an environment (e.g. `production`, `ci`) |
| `LANGFUSE_RELEASE` | No | Tags every observation with a release identifier |
| `LANGFUSE_DEBUG` | No | Set to `true` for SDK debug logging (dropped spans, export errors) |

Copy `.env.example` to `.env` and fill in the Langfuse values. The SDK reads the credential variables
itself on first use; the code never passes keys explicitly.

---

## Running Locally with Tracing

1. Add your Langfuse keys to `.env`:
   ```
   LANGFUSE_PUBLIC_KEY=pk-lf-...
   LANGFUSE_SECRET_KEY=sk-lf-...
   ```
2. Run the pipeline normally — traces appear in the Langfuse dashboard automatically:
   ```bash
   npm run run-pipeline -- --pr 12345
   ```
3. Open [cloud.langfuse.com](https://cloud.langfuse.com) → your project → **Traces** to see the result.

To disable tracing while keeping the keys in `.env`:
```
LANGFUSE_ENABLED=false
```

## Disabling Tracing in Tests

All tests run with `LANGFUSE_ENABLED=false`. This is enforced in CI via the `unit_tests.yml` workflow env
and locally via proxyquire stubs in `test/scripts/run-pipeline.spec.ts`.

When disabled, no OpenTelemetry tracer provider is registered, so every observation is non-recording,
nothing is exported, and scores are dropped. Tests that directly call `filterPR` or `distillPR` are
unaffected — tracing is optional and defaults to `undefined` in tests.

## Trace Structure

Each `processSinglePR` call produces **one Langfuse trace** whose root observation is:

```
memory-pipeline-pr   (root span — input: { prNum, repo, url }; output: { decision, reason, distillStatus? })
├── span: scrape          (no LLM — input: prNum, repo; output: fileCount)
├── generation: triage-classify
└── generation: distill-draft
    score (trace-level): distill-outcome (1 = written, 0 = flag-for-human)
```

The trace name, session id, tags (`[memory-pipeline, <repo>]`), and metadata (`{ prNum, repo }`) are
**propagated to every observation** in the trace, including the cost-bearing generations, so session
and tag aggregations in Langfuse v4 include token and cost data.

Overall input and output live on the **root observation**; trace-level input/output setters are
deprecated in Langfuse v4 and are not used.

The trace **id is generated by Langfuse per run** — it is not derived from the PR number. Reprocessing
the same PR (the default `--since` lookback overlaps on a schedule) therefore produces a distinct trace
each time rather than mutating an earlier run's session. The PR identity lives in the root `input`,
`tags`, and `metadata`, so it stays filterable.

All traces from a single `run-pipeline` invocation share one **session ID** (a UUID generated at the
start of `runPipeline`), visible in the Sessions view.

## Naming Conventions

Follow these when adding instrumentation to new workflows:

| Concept | Convention | Example |
|---|---|---|
| Trace name | `<workflow>-<entity>` (descriptive, not unique) | `memory-pipeline-pr` |
| Trace id | Generated by Langfuse — do not hand-build from entity ids | — |
| Session ID | UUID per run, groups its traces | `a3f1…` |
| Span names | `<stage>` or `<stage>:<substage>` | `scrape` |
| Score names | `<stage>-outcome` | `distill-outcome` |
| Tags | Workflow name + entity scope | `['memory-pipeline', repo]` |
| Metadata | String values only, ≤ 200 chars (the SDK drops anything else) | `{ prNum: '42', repo }` |

## Adding Instrumentation to a New Workflow

1. Import from `src/observability`:
   ```typescript
   import { withTrace, observeGeneration, scoreTrace, shutdownLangfuse, type TraceRoot } from '../observability';
   ```

2. Wrap the workflow entry point in `withTrace`. It opens the root observation, propagates
   `sessionId`/`userId`/`tags`/`metadata` to everything created inside the callback, records a
   thrown error on the root with `level: 'ERROR'`, and always ends the root:
   ```typescript
   await withTrace(
     {
       name: 'research-supervisor',
       sessionId,
       input: { runId },                 // identity only, not whole objects
       tags: ['research-supervisor'],
       metadata: { runId },              // string values only
     },
     async (root) => { /* steps below */ }
   );
   ```
   Everything that should carry the session id must be created **inside** the callback; observations
   started before it are not retroactively updated.

3. Wrap each model call in `observeGeneration`. It records the prompt, the parsed output,
   `usageDetails` (API path) or `costDetails` (Claude CLI path), and ends the generation with
   `level: 'ERROR'` on failure. Build the chain with `createLangChainStructuredChain` (API) or
   `createStructuredCliChain` (CLI) so `invoke` returns a `GenerationResult`
   (`{ parsed, model?, usage?, costUsd? }`):
   ```typescript
   const parsed = await observeGeneration(root, { name: 'classify', model, input: prompt },
     () => chain.invoke(prompt));
   ```

4. Use `root.startObservation()` for non-LangChain operations:
   ```typescript
   const span = root.startObservation('my-operation', { input: { key: value } });
   // ... do work ...
   span.update({ output: { result } }).end();
   ```

5. Score terminal outcomes and set the root output:
   ```typescript
   scoreTrace(root, { name: 'my-outcome', value: success ? 1 : 0 });
   root.update({ output: { result } });
   ```

6. Shut Langfuse down **once** at the end of the whole run, not per item. It flushes buffered spans,
   then queued scores, and awaits in-flight requests:
   ```typescript
   await shutdownLangfuse();
   ```

7. In tests, stub the observability module with proxyquire. Record calls so the spec can assert the
   root was actually passed to each stage (see `test/scripts/run-pipeline.spec.ts` for a full
   recording spy):
   ```typescript
   const root = { startObservation: () => ({ update() { return this; }, end() {} }), update: () => {} };
   '../observability': {
     withTrace: (_opts, fn) => fn(root),
     scoreTrace: () => {},
     shutdownLangfuse: async () => {},
     '@noCallThru': true,
   }
   ```
   To assert what would reach Langfuse without a network, see `test/observability/index.spec.ts`: it
   swaps the OTLP exporter for an `InMemorySpanExporter` and checks span attributes directly.

## Sensitive Data

The memory pipeline only traces **public** `medic/cht-core` PR data (number, repo, URL, and the LLM
prompts/completions captured in direct generations), so no masking is configured today. The root
`input` is deliberately set to PR identity only (`{ prNum, repo, url }`) rather than the whole scraped
object — keep it that way.

If this pattern is reused for a workflow that handles private or user data, mask or omit it before it
reaches an observation `input`, `output`, or prompt (the span processor supports a `mask` function).

## Token and Cost Data

Every generation records the model, prompt, completion, latency, and errors. Cost data differs by path:

| Path | What is sent | How Langfuse prices it |
|---|---|---|
| API (OpenRouter / Anthropic) | `usageDetails` from LangChain `usage_metadata` (input/output/total tokens) and the provider's reported model name | Inferred from the model definition in Langfuse |
| Claude CLI (`claude -p`) | `costDetails.total` from the CLI's `total_cost_usd` and the configured model name; the CLI reports no token counts | Ingested USD directly |

## Delivery Semantics

Spans are exported over OTLP/HTTP by a batching span processor with a 3-second request timeout. The
OTLP exporter applies its own retry/backoff on transient failures within that time. Scores go through
the client's queue, which uses the SDK default timeout of 60 seconds (`@langfuse/client` 5.11.1 ignores
its `timeout` option). `shutdownLangfuse()` flushes both queues before `process.exit` and only logs a
warning when Langfuse is unreachable, so tracing never changes a run's exit code.

## Langfuse v4 Notes

- Ingestion is OpenTelemetry (`/api/public/otel/v1/traces`); the legacy batch ingestion API used by
  the old `langfuse` v3 npm package is deprecated on Langfuse Cloud and removed on 2026-11-16.
- Trace-level LLM-as-a-judge evaluators are deprecated. Evaluate on observations instead: the
  `memory-pipeline-pr` root span carries the overall input/output, and `triage-classify` /
  `distill-draft` carry the prompts and completions. Observation evaluators cannot read sibling or
  child observations, so put every variable an evaluator needs on the observation it targets.
- No exports (Blob Storage, PostHog, Mixpanel) are configured. The only Public API call is score
  creation: `@langfuse/client` sends `score-create` events to `/api/public/ingestion`, which Langfuse
  keeps supporting after the 2026-11-16 cutover.
