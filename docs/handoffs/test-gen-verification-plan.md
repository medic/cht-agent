## The incident that motivates this

On the Maisha m4 run (contact-summary defaulter predicate), test-gen produced
two harness specs that shipped in the PR bundle and were **never executed by
anything**:

- `test/tasks/immunization_service.agent.spec.js` — report fixture used
  `vaccines_received` where the config reads `group_vaccines.vaccines_given`
  → parsed doses always ∅ → its "true defaulter stays flagged" test passed
  vacuously and its AC1 test failed when run by hand.
- `test/contact-summary.agent.spec.js` — household fixture had a one-level
  parent while `isNTDEnabled` unconditionally walks
  `lineage[0].parent.parent.parent.parent._id` → TypeError before the
  predicate under test ever evaluated.

Nothing caught this because of three independent gaps:

1. **Test-gen is the terminal graph node** (`development-supervisor.ts`:
   `generateCode → validateImpl → [applyXlsformFix] → generateTests → END`).
   Its output is validated by nothing, executed by nothing, repaired by
   nothing.
2. **Pinned `qaSpecs` displace generated specs in tier-2**
   (`cht-conf-tier2.ts` `findTier2Specs`: qaSpecs present → run EXACTLY
   those). m4 pinned three regression specs, so QA never touched the agent
   specs. (Form tickets like m5/m8/m7 got lucky: the per-artifact default
   selection includes `<form>.agent.spec.js`, so tier-2 did run theirs.)
3. **The validator runs before test-gen exists**, so it files stale
   "ships with 0 test files" recommendations that HC5 then makes a human
   adjudicate (m4's only deferred item was exactly this).

## Design principle

Same rule the rest of this pipeline lives by: an artifact is trustworthy only
when a deterministic run proves it, not when an LLM says it looks right. For
a generated spec, "proven" means the full red→green discipline:

- **RUNS** — mocha executes it with no fixture/environment crash;
- **RED** — it FAILS against the pre-fix sources (it can detect the bug);
- **GREEN** — it PASSES against the fixed sources (the fix satisfies it).

m4's specs failed all three, silently. A spec that cannot be proven must not
ship — dropping it loudly beats shipping a vacuous or broken test.

## The feature, in four parts

### Part 1 — verifyTests node (the core)

New graph node after `generateTests`, before END:

```
generateTests → verifyTests → END
                    ↺ (repair loop, bounded)
```

Mechanics per generated spec file (reusing existing machinery — nothing new
to invent):

1. Build a sandbox copy of the config repo with node_modules symlinked —
   exactly what `createConvertSandbox` + the offline-compile path already do
   (`cht-conf-runner.ts`). Copy the staged fix files AND the staged spec in.
2. **GREEN run**: repo-pinned mocha over the spec (reuse the `runTier2`
   runner: env allowlist, TZ, timeout, tail capture). Must pass.
3. **RED run**: revert the fix files inside the sandbox to their baseline
   content (the tier-2 baseline machinery `runTier2Baseline` already knows
   how to construct pre-fix sources from `fixFiles`). Must FAIL — and fail
   on an assertion, not an environmental crash
   (`isTier2EnvironmentalFailure` already classifies this).
4. Record a per-spec verdict matrix: `{ran, red, green, tail}`.

Cost note: each run boots headless Chromium via the harness (~30–90 s per
spec file). Two runs × N spec files is real wall-clock — hence opt-in first
(Part 4).

### Part 2 — bounded repair loop

On any verdict other than ran+red+green, re-invoke the test-gen module with
the evidence as feedback (the mocha tail names the broken fixture — m4's
failures were both one-line diagnoses) and regenerate ONLY the spec files.
Bound it: `TEST_GEN_MAX_REPAIRS` default 2, mirroring the descriptor loop's
philosophy (the budget guard in `test-gen/lib/budget.ts` already exists to
keep spec churn bounded).

Exhaustion is an honest self-skip, never a silent ship:

- drop the spec from `filesWritten` (it must not enter the PR bundle),
- record a deferred recommendation ("generated spec could not be proven
  red→green after N repairs; dropped — evidence: <tail>") so HC5/PR.md carry
  it,
- do NOT fail the development phase: the fix's own proof (XLSForm apply /
  compiled-settings oracle + QA) is independent of the spec.

The repair prompt must state the invariant explicitly: the spec is wrong
until proven otherwise — the FIX is already machine-verified; a spec that
fails green indicts the spec, not the fix, unless the operator says
otherwise at HC2.

### Part 3 — tier-2 selection: pinned specs AUGMENT, not displace

`findTier2Specs`: when `qaSpecs` are pinned, also include any existing
`test/**/<artifactName>*.agent.spec.js` (and the artifact's default agent
specs for settings tickets). One function + its unit tests. This is
independently shippable and would alone have surfaced m4's broken specs at
QA time (as a tier-2 failure with baseline attribution) instead of never.

Interaction to respect: `tier2FailuresArePreExisting` baseline attribution
still works because the baseline run reverts `fixFiles`, which includes the
generated specs (an untracked spec vanishes on revert — the runner's missing-
spec self-skip already handles that case; add a test for it).

### Part 4 — sequencing, flags, and the stale-validator fix

- **Flag**: `--test-verify` (CLI) / `TEST_GEN_VERIFY=1`, default OFF at
  first (wall-clock cost), flipped to default ON once it has survived a few
  real runs. Part 3's selection change ships default-on immediately.
- **Validator staleness**: one line in the validation prompt — "test specs
  are generated by a LATER stage; do not report their absence as a defect."
  Kills the m4-style stale deferred item at the source. (Alternative —
  moving test-gen before validation — is wrong: validation feedback drives
  code refinement iterations, and specs would be regenerated per iteration.)
- **PR.md provenance** (`pr-bundle.ts`): the "Tests added" section gains the
  verdict per spec: `proven red→green (RED: 3 failing pre-fix, GREEN: 6
  passing post-fix)` or is absent because unproven specs are dropped. A
  reviewer can then trust a shipped spec without re-deriving it.

## What this would have done to the m4 run

1. verifyTests GREEN run: contact-summary spec crashes in `isNTDEnabled` →
   repair 1 fixes the lineage fixture; tasks spec AC1 fails → tail shows ∅
   parsed doses → repair fixes the field name.
2. RED run: both specs fail against baseline (discriminating) → proven.
3. Tier-2 (Part 3) runs pinned 3 + 2 agent specs → 130+6 passing.
4. HC5 opens with zero deferred items (the stale "0 test files" item never
   files). PR.md ships specs annotated "proven red→green".

## Non-goals

- No LLM-judged spec quality: the red→green matrix is the whole verdict.
- No full-suite run inside the dev phase (tier-2/QA owns regression
  breadth); verifyTests runs ONLY the specs this ticket generated.
- No repair of PARTNER specs — only agent-generated ones are ever touched.
